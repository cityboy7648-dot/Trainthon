# PLAN

구현 계획. 제품이 뭔지는 [README.md](../README.md). 최종 목표에서 역으로 내려왔고, 구현은 아래에서 위로 올라간다.

## 최종 목표

로그인한 사용자가 사이트 URL을 넣고, 추천 캠페인과 레퍼런스를 고르면, 한 화면에서 브랜드 에셋 / 인스타 피드 / 영상을 받는다. 영상은 "생성 중"으로 시작해 완료되면 같은 화면에서 재생된다. 결과는 저장되어 다시 볼 수 있다.

| 게시                 | 1차는 일정표와 소재 생성까지. 채널 API를 연결한 뒤 자동 게시 추가                   |

## 역순 사슬

```
6. 결과 화면    브랜드 에셋 / 피드 / 영상(생성 중 → 완료)   저장·재방문·다운로드
5. 캠페인 실행  캠페인 정의 → 산출물 목록 → 생성기 호출 → assets 저장
4. 생성기       텍스트(캡션/카피) / 이미지(gpt-image-2) / 영상(Higgsfield)
3. 선택 화면    캠페인 추천 3개 → 선택,  레퍼런스 라이브러리 → 선택
2. 분석 에이전트 URL → 브랜드 프로필
1. 뼈대         Next.js, Supabase, Auth, env, API 클라이언트, 정의 파일
```

사슬은 무엇이 무엇에 의존하는지다. 실제 구현 순서는 아래 "구현 순서".

## 데이터

### 브랜드 프로필 (분석 에이전트 출력 = 생성기 입력)

```
name, tagline, industry,
logo_url, palette[], font_feel,
voice, mood_keywords[],
products[] { name, image_url, description, price },
target_audience,
source_url, analyzed_at
```

### 레퍼런스 (라이브러리 항목. 코드에 정의)

```
key, name, description,
sample_images[]        // 레포에 포함. gpt-image-2로 1회 생성
image_prompt_hints,    // 이미지 생성에 붙는 스타일 지시
voice_hints            // 캡션 말투 지시
```

초기 6개. 미니멀 화이트 / 따뜻한 필름 / 볼드 컬러 / 다크 프리미엄 / 내추럴 라이프 / 팝 일러스트. 개수·구성은 바뀔 수 있다.

### 캠페인 (내부 목록. 코드에 정의)

```
key, name, goal,
duration_days,
channels[],
schedule[] {
  day,                 // 캠페인 시작일 기준 상대 일자
  channel,
  format,              // feed | carousel | reel | story 등
  purpose,             // 이 게시물이 캠페인에서 맡는 역할
  outputs[] {
    kind: image | caption | video,
    count, aspect, text_in_image: bool, brief
  }
}
```

캠페인은 단일 산출물 묶음이 아니다. 정해진 기간 동안 어떤 채널에 어떤 포맷을 어떤 순서로 게시할지 정한 재사용 가능한 일정이다. 브랜드마다 카피와 비주얼은 달라지지만 일정의 역할과 순서는 같다.

Reel·Carousel·Feed·Story는 채널이 아니라 채널 안의 포맷이다. 캠페인 하나가 여러 채널과 포맷을 함께 쓸 수 있다.

1차는 일정표와 게시물 소재를 만든다. 실제 예약 게시에는 플랫폼별 OAuth, 게시 API, 예약 작업, 실패 재시도가 필요하므로 후속 단계에서 연결한다.

#### 설계 원칙

캠페인은 포맷을 날짜에 배치해서 만들지 않는다. 다음 순서로 역산한다.

1. 목표: 캠페인이 끝났을 때 보는 사람에게 일어나야 하는 일 한 문장
2. 보는 사람의 상태: 캠페인 시작 시점에 그 사람이 우리를 얼마나 아는가
3. 방식: 그 상태를 목표로 바꾸는 방법. 반복, 문제 제시, 반론 답변, 긴장과 해소 등
4. 게시물: 그 방식에 필요한 것만. 채널·포맷·순서·기간은 여기서 나온다

목표가 다르면 구조가 달라야 한다. 구조가 비슷하면 하나로 합친다.

#### 전제

- 사용자는 두 종류. 웹/앱 서비스를 만든 1인 개발자·소규모 팀, 그리고 상품이 있는 소상공인·소규모 이커머스
- 사용자 계정은 대부분 팔로워가 거의 없다. 따라서 참여 유도(댓글·투표·공유)를 목표로 하는 캠페인은 만들지 않는다. 도달은 숏폼 알고리즘, 광고, 팔로워 없이도 노출되는 텍스트 플랫폼(스레드·링크드인)에서 온다
- 사이트에 없는 정보(할인율, 출시일, 만든 사람 이야기)는 사용자 입력으로 받는다. 추측해서 채우지 않는다

#### 일정

`D1`은 캠페인 시작일. `D-n`, `D+n`은 기준일(출시일·프로모션 시작일) 기준.

시그니처 그리드. 상세는 아래 "캠페인 상세 — 시그니처 그리드".

3초 소개. 하루 1개, 영상 9:16 + 커버 1장 + 캡션 1개. 같은 영상을 세 플랫폼에 올린다. 문제 5개는 브랜드 프로필의 `products`, `target_audience`에서 뽑는다. 첫 3초는 항상 문제 문장, 제품은 그 뒤에 나온다.

망설임 제거. 하루 캐러셀 1세트(4~5장, 4:5) + 스토리 1장(9:16) + 캡션 1개. 사이트에 해당 정보가 없으면 그 날은 건너뛰고 사용자에게 알린다.

| --- | ------------------------------ |
| D1  | 왜 이 가격인가                 |
| D2  | 어떻게 받나 / 어떻게 시작하나  |
| D3  | 환불·보증·무료 체험            |
| D4  | 다른 선택지와 무엇이 다른가    |
| D5  | 실제로 쓰면 어떤가             |
| D6  | 정리 캐러셀 + 스토리 질문 받기 |

카운트다운 런칭. 입력: 출시일, 출시하는 것의 이름.

만든 사람 시리즈. 주 2회, 글 1편을 Threads와 LinkedIn에 톤만 바꿔 올린다. 텍스트 카드 이미지 1장 선택. 사이트에 없는 내용이므로 시작할 때 8개 질문에 사용자가 짧게 답한다. 에이전트는 그 답을 글로 만든다.

사용 장면. 하루 피드 1장(4:5) + 스토리 1장 + 캡션 1개. 상황 7개는 `target_audience`, `products`에서 뽑는다. 각 장은 사람·시간·장소·하는 일 중 하나가 다르다. D7은 7개 장면을 모은 캐러셀.

기존 방식 vs 우리. 하루 캐러셀 1세트(3장: 기존 방식 / 우리 / 차이) + LinkedIn 글 1편. 비교 대상은 경쟁사 이름이 아니라 방식(수작업, 엑셀, 외주 등). 사이트에 근거 없는 주장은 넣지 않는다.

| 날  | 비교 축                                      |
| --- | -------------------------------------------- |
| D1  | 걸리는 시간                                  |
| D2  | 드는 비용                                    |
| D3  | 결과의 차이                                  |
| D4  | 시작하는 난이도                              |
| D5  | 정리. 언제 기존 방식이 낫고 언제 우리가 낫나 |

상품 하나씩. 하루 상품 1개, 피드 1장(4:5) + Pinterest 핀 1장(2:3) + 캡션 1개. 템플릿 하나를 전 상품에 똑같이 쓴다. 상품 이름·가격·한 줄 설명은 `products`에서. 상품이 10개를 넘으면 사용자가 고른다.

시즌 기획. 입력: 시즌 이름, 기준일. 광고 소재는 1:1, 4:5, 9:16.

| 날    | 채널·포맷                  | 내용                       |

| D-10  | Instagram 피드 + Meta 광고 | 시즌 문맥 속 상품          |

| D-1   | Instagram 스토리           | 마지막 주문                |
| D-day | Instagram 피드             | 시즌 당일 메시지           |

숫자로 증명. 하루 피드 1장(1:1, 숫자가 크게) + LinkedIn 글 1편. 숫자·사실은 사이트에 공개된 것만(사용자 수, 리뷰 수, 재료·원산지, 제작 기간, 운영 기간 등). 5개가 안 나오면 있는 만큼만 만들고 사용자에게 알린다.

분야 지식 시리즈. 주 3회 캐러셀 1세트(5~~7장, 4:5) + Threads 글 1편 + Pinterest 핀 1장. 주제 6개는 `industry`, `products`에서 뽑는다. 1~~6장은 브랜드 없이 팁만, 마지막 장만 브랜드와 CTA.

사전 등록. 입력: 등록 URL, 만들고 있는 것 한 줄. 출시 전이므로 제품 화면은 안 보여 준다.

| 날  | 채널·포맷                   | 내용                          |
| --- | --------------------------- | ----------------------------- |
| D1  | Threads + LinkedIn          | 이 문제를 겪는 사람이 있나    |
| D2  | Threads                     | 왜 기존 해법이 안 되나        |
| D3  | Threads + LinkedIn          | 우리가 만들고 있는 것         |
| D4  | Instagram 스토리            | 등록 링크                     |
| D5  | Threads                     | 등록자 수 또는 진행 상황      |
| D6  | LinkedIn                    | 누구를 위해 만드나            |
| D7  | Threads + LinkedIn + 스토리 | 등록 마감 또는 다음 소식 예고 |

후크 테스트. 광고 소재 4세트. 세트 = 후크 문장 1개 × 이미지 1:1·4:5·9:16 + 헤드라인·본문·CTA. 상품과 이미지는 같고 후크만 다르다(문제형, 결과형, 비교형, 질문형). 5일 동시 노출. 결과 판단은 사용자가 광고 관리자에서 한다. 우리는 소재와 비교표만 만든다.

공감 한 줄. 하루 글 1편, Threads와 X에 같은 글. 이미지 없음. D1~D6은 제품·브랜드 언급 없이 타겟이 겪는 상황 한 줄. D7만 "그래서 이걸 만들었다" + 링크. 상황은 `target_audience`, `products`에서 뽑는다.

#### 캠페인 상세 — 시그니처 그리드

공통 규칙

- 1:1, 1080×1080. 9장 전부 같은 여백, 같은 로고 위치(왼쪽 위 작게), `font_feel`에 맞는 서체 1종
- 배경은 두 톤만. `palette[0]`(브랜드 주색)과 밝은 중립. 홀수 장 주색, 짝수 장 중립
- 이미지 안 텍스트는 헤드라인 1줄(12자 이내) + 보조 1줄까지. 그 이상은 캡션으로
- 캡션 구조: 첫 줄(이미지 헤드라인을 반복하지 않는 한 문장) → 2~3문장 → 프로필 링크 안내 → 해시태그 5개(브랜드 1, 업종 2, 타겟 2)
- 게시 순서는 역순. 인스타 그리드는 최신 게시물이 왼쪽 위에 오므로, 완성 그리드가 1번(이름·로고)부터 9번(CTA)까지 읽히려면 D1에 9번을, D9에 1번을 올린다. 팔로워 0 전제이므로 매일 보는 사람보다 완성 그리드를 우선한다
- 사람 얼굴은 생성하지 않는다. 뒷모습·손·실루엣까지만
- 프로필 소개문 1개(150자): 한 문장 소개 + 누구를 위해 + 링크. D1에 함께 교체

### Supabase 테이블

이 표가 스키마의 기준이다. 테이블·컬럼을 추가하려면 이 표를 먼저 고친다.

```
brands      id, user_id, source_url, profile jsonb, created_at
runs        id, brand_id, campaign_key, reference_key, status, created_at
assets      id, run_id, kind, status, storage_path, provider_request_id, meta jsonb, created_at
```

`status` 값: `pending`, `processing`, `done`, `failed`.

Storage 버킷 `assets`. 이미지·영상 결과는 제공자 URL에서 받아 여기로 옮긴다 (Higgsfield 결과 보관 7일).
RLS: 본인 `user_id` 행만.

## 분석 에이전트

서버 라우트에서 실행. LLM + 도구.

- 도구: HTML 가져오기, 링크된 이미지/OG/파비콘 수집, CSS 색상 추출, 필요 시 하위 페이지 1~2개 추가 fetch
- 출력: 브랜드 프로필 스키마에 맞춘 구조화 출력
- 실패는 그대로 화면에 보여 준다. 빈 프로필로 넘어가지 않는다.

스크린샷은 1차에서 뺀다. HTML+이미지로 부족하면 추가한다.

## 캠페인 추천

브랜드 프로필 + 캠페인 목록 전체 → LLM → 상위 3개 + 각 한 줄 이유. 사용자에게는 3개만.

## 생성 흐름

1. 사용자가 캠페인 1개, 레퍼런스 1개 선택 → `runs` 생성
2. 실행기가 캠페인 `schedule[]`과 각 일정의 `outputs[]`를 순회하며 `assets` 행을 `pending`으로 만든다
3. 텍스트/이미지: 동기 생성 → Storage 업로드 → `done`
4. 영상: Higgsfield 요청 → `provider_request_id` 저장 → `processing`. 웹훅 또는 폴링으로 완료 시 다운로드 → Storage → `done`
5. 결과 화면은 `assets`를 구독해 완료되는 대로 채운다

영상 입력 이미지는 같은 run에서 만든 피드 이미지 중 하나를 쓴다.

## 구현 순서

앱 셸은 완료. URL 입력 전 홈은 사이드바 없이 보이고, URL 제출 후 진입하는 앱 화면은 `(app)/layout.tsx`의 공통 사이드바를 공유한다. 각 탭이나 페이지에서 사이드바를 따로 만들지 않는다. 한 단계 = 한 브랜치. 끝나면 화면에서 확인 가능해야 한다. 프론트는 디자인 레퍼런스를 받은 뒤 시작. 프론트 데이터는 전부 `src/mock/`.
